Toolmux guide

One place to connect agents to tools and model providers.

What each thing means

Agent
A machine identity such as a Hermes profile, OpenClaw agent, Codex, or Claude Code. Its token identifies tool and model calls.
Connection
An upstream service or account, with its protocol and saved authorization.
Tool
One callable action from a connection. A grant decides whether an agent may call it.
Model provider
An inference service and its credentials. The shared catalog exposes provider/model IDs. Agents select their own models.
User
A person signing into this interface. Browser roles are separate from agent tokens.

Connect tools

  1. Create an agent or use Agents → Discover installed.
  2. Add a connection: remote MCP, imported local MCP, HTTP API, or command.
  3. Authorize and check the connection. MCP discovers its tools; HTTP and commands use explicitly configured tools.
  4. Assign a connection or select individual tools on the agent page.
  5. Configure the client MCP endpoint as {{.Endpoint}} with its agent bearer token.

Whole-connection assignments include future tools. Removing an individual tool switches that connection to individual grants, so refresh cannot restore it. A grant does not grant access to another agent.

Configure inference

Add the provider's base URL, protocol, authentication, and model IDs under Models. Discover models when supported. Use {{.GatewayURL}}/v1 in OpenAI-compatible clients, with the agent token as the API key. Native Anthropic clients use {{.GatewayURL}}. Model IDs are provider/model.

Protocols and credentials are independent. Supported native authentication includes bearer, custom header, basic, OAuth client credentials, and no authentication. Azure uses deployment names. Provider credentials are encrypted and are not copied into agents.

Codex subscriptions

Start the optional LiteLLM model bridge and configure it as a provider. Codex sign-in displays the account state and interactive device code. The bridge owns refresh and persistent account tokens. Use streamed Responses and a named Responses provider in Hermes; model availability depends on the signed-in account. See the provider setup guide for bridge deployment.

A local bridge's reachable model catalog does not prove that every underlying account can infer. The separate Codex authorization state covers that account. Other cloud identities and protocol translations depend on their bridge adapters.

Rotate agent tokens

Choose Rotate beside a token. If matching local references are found, a review dialog lists their paths and offers to replace them. It updates the same token wherever found in supported tool and model configuration files, then revokes the old one. Restart running agents to reload their configuration.

Detection covers registered Hermes, OpenClaw, Codex, and Claude Code installations. Exact token matches are required. Environment keys outside the listed files, remote/WSL profiles, secrets managers and unknown layouts need manual updates. No upstream provider or subscription credentials are rotated by this operation.

If a file update fails midway, both tokens remain valid to avoid disconnecting partially updated clients. The log records the incomplete rotation; finish updating and revoke the old token manually.

Authorization checks and alerts

Toolmux checks enabled connections and model catalogs on startup and at the interval in Settings. Checks run four at a time, have timeouts, and do not overlap. OAuth connections refresh through their existing authorization flow. Codex is checked every 30 seconds and refreshed near expiry.

Connected means the check succeeded, not that every possible tool/model call has been tested. Unknown means a non-inference authorization check was unavailable. A rejected credential is shown as Needs authorization; network failures are shown separately.

Administrators can save an HTTPS webhook in Settings. A Slack incoming webhook works directly: each request contains a small JSON text message. Alerts are sent when authorization becomes required and when that resource recovers. Repeated failures do not repeatedly notify. Test delivery is an explicit button.

Failed deliveries retry twice, after 5 and 10 minutes. Requests time out after 10 seconds; redirects are not followed. The event ID is sent in X-Toolmux-Event-ID; receivers may use it to deduplicate retries. Delivery is at least once, so an acknowledgement lost in transit can cause a duplicate. Changing settings clears queued alerts.

Operational logs keep transitions, rotations and delivery outcomes for 14 days, capped at 2,000 events. Activity shows tool/model calls and reported usage. Neither stores prompts, arguments, outputs or secrets.

User roles

Administrator: users, roles, monitoring destinations, shared Codex sign-in, and configuration. Operator: agents, tokens, grants, connections and providers. Viewer: read configuration and logs. Everyone can change their own password. The last enabled administrator cannot be removed or demoted.
